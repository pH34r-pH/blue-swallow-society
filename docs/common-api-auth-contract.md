# Common Society API resource contract (code only)

One single-tenant Microsoft Entra resource uses v2 access tokens, application ID URI `api://<API_CLIENT_ID>`, and the proposed scopes `Owner.Read`, `Observations.Upload`, `Entities.Write`, plus `World.Manage` for explicit orbital source maintenance. These names require owner-approved scope provisioning and consent; this source change creates no registration, role, grant, secret, permission, hosting resource or deployment.

## Stable runtime-neutral interface

The canonical validator is `vm/cybermap-api/src/api-access-token.cjs`. `createApiTokenValidator({ getConfig, keySet, loadJose, now })` returns an async `verifyApiAccessToken(rawBearer, requiredScope)`. Production defaults use the tenant's fixed Microsoft JWKS endpoint and JOSE RS256 verification. Dependency injection is only trusted server/test construction, never request configuration. The shared Functions adapter is `api/_lib/api-access-token.js`: `await requireApiAccessToken(context, req, scope)` returns a frozen `{ tenantId, objectId, operatorId, scopes }`, or null after setting a no-store error response. Stop on null. Do not derive actor/owner from request payloads or platform headers. The Functions image copies this single canonical implementation; the VM package ships it directly.

Validation requires exact tenant v2 issuer, scalar API-client GUID audience (not application ID URI), tenant GUID and approved immutable owner object GUID, `ver=2.0`, valid signature/exp/nbf/iat and the operation's exact delegated `scp`. App-only/roles-only claims, Web ID tokens, Graph tokens, old application sessions and principal headers do not authorize this common API. Scope names are case-sensitive. Unknown scopes fail closed. Claims are never logged or returned wholesale.

New entity reads require Owner.Read; mutations require Entities.Write. Upload requires Observations.Upload **plus independently validated server-bound installation namespace**. A user token alone does not identify an installation. Existing ingest transactionality, immutable capture values, device credentials and durable replay remain in force until a separately tested upload migration is integrated. No new mutation may use the transitional read proof.

## Configuration and approval

Nonsecret server settings: `BLUE_SWALLOW_ENTRA_TENANT_ID`, `BLUE_SWALLOW_ENTRA_API_CLIENT_ID`, `BLUE_SWALLOW_ENTRA_OWNER_OBJECT_ID`. Values are exact lowercase GUIDs. Web/BFF still uses `BLUE_SWALLOW_ENTRA_CLIENT_ID` for its distinct confidential Web client, `BLUE_SWALLOW_PUBLIC_ORIGIN` and the existing server-only credential/session settings documented in owner-entra-cutover.md. API client and Web client IDs must differ. Android uses its separately approved public client and requests `api://<API_CLIENT_ID>/Owner.Read` and `api://<API_CLIENT_ID>/Observations.Upload`; it does not request Entities.Write. Web ordinary login requests Owner.Read. The explicit Entities Enable editing action requests incremental Entities.Write and binds it to the owner session; see entity-edit-authorization.md. No OBO is needed for this single logical API resource.

## Web cache and lifetimes

When BLUE_SWALLOW_ENTRA_API_CLIENT_ID is configured, the normal confidential authorization-code + PKCE flow requests Owner.Read. MSAL keeps delegated credentials in its server-process memory cache. A bounded session registry retains that client/account for at most the five-minute application session (128 concurrent entries), uses acquireTokenSilent, and clears on logout/expiry. No API token or refresh credential is persisted to browser storage, returned by the session endpoint, or written to disk. No new cache infrastructure is created. Explicit entity editing also checks the cache's requested-scope intent before writes, so a broader MSAL token cannot elevate a read-only session. Restart or routing to an instance without the entry requires login again; source tests do not establish multi-instance live reliability.

`api/_lib/owner-read-auth.js` supports verified API bearer reads and the existing browser session. With API configuration it requires the session's server-side MSAL cache and forwards a delegated API token. Cache failure does not downgrade to a custom proof. Without that configuration, the existing signed proof remains transitional and read-only. VM read endpoints validate Owner.Read before store access. Existing global/tile proxy wrappers still retain their transitional path pending cutover; this PR does not claim every adapter has migrated.

Microsoft access-token expiry is whatever validated exp declares (commonly 60–90 minutes), distinct from the five-minute application session and 30-second transitional read proof. Logout clears the Web cookie/cache, but does not revoke a copied access token; it can remain usable until expiry unless upstream policy invalidates it. Existing issued APK SAS links last five minutes and downloaded artifacts cannot be revoked. Android captures/retry queues must remain independent of token expiry. No refresh-token persistence or offline queue erasure is introduced here.

Deployment remains on hold for approved exact identities/redirects/scopes/consent, isolated real Microsoft owner/wrong-owner validation, Android installation-bound upload migration, direct-backend tests, and the pending hosting choice. Synthetic signed-token tests prove code behavior only.

World orbital source reset is a separate maintenance CLI operation requiring canonical exact-owner World.Manage validation, the current failed acquisition attempt ID, and a review reason. Owner.Read and Entities.Write cannot reset it. This source change does not provision or consent World.Manage, expose a browser mutation, or activate acquisition/migration. See world-selected-orbits.md.
